### Current architectural state

The application currently has:

```text
Qt 6 Widgets application
├── Project model and JSON persistence
├── Project tree
├── Project/file creation
├── Build-output panel
├── Generic EditorBackend API
├── QScintillaBackend
├── VimBackend via QTermWidget
├── Optional KTextEditorBackend
├── Runtime editor selection
├── Multi-session Vim tabs
├── Save/discard/close lifecycle handling
└── Dark theme application/editor presentation
```

Significant is that the editor abstraction is no longer theoretical. We now have three substantially different editor backend implementations:

```text
QScintilla:
- native embedded editor
  
Vim:
- external interactive editor hosted through QTermWidget
    - Vim instances load the user's .vimrc and plug-ins
  
KTextEditor:
- optional KDE/KatePart-based editor

```

This validates the central design decision of a generic EditorBackend API.  
  
  
### Soon: complete and stabilize editor integration

#### 1. Audit KTextEditor API compliance

Although KTextEditor is a build-time option for those who want it, it needs to fully implement the EditorBackend API.

The KTextEditor backend currently compiles when enabled, but it has known incomplete behavior:

```text
fontPointSize()
setFontPointSize()
fontPointSizeChanged()
```

| EditorBackend operation | QScintilla | KTextEditor | Vim |
|---|---:|---:|---:|
| `widget()` | yes | yes | yes |
| `openFile()` | yes | yes | yes |
| `saveCurrentFile()` | yes | yes | yes |
| `saveAllFiles()` | yes | yes | yes |
| `discardAllChanges()` | yes | yes | yes |
| `closeCurrentFile()` | yes | yes | yes |
| `closeAllFiles()` | yes | yes | yes |
| `currentFilePath()` | yes | yes | yes |
| `isModified()` | yes | yes | yes |
| `hasModifiedFiles()` | yes | yes | yes |
| `fontPointSize()` | yes | provisional/incomplete | yes |
| `setFontPointSize()` | yes | provisional/incomplete | yes |


The KTextEditor backend should either gain real font-size support or explicitly advertise that the operation is unsupported. Since KTextEditor is an optional build, this should be resolved before calling the editor API stable.  
  
  
#### 2. Finish the QScintilla color theme

This is relatively contained and should follow the KTextEditor audit.

The QScintilla theme should eventually be extracted from `QScintillaBackend` into a reusable abstraction, for example:

```text
EditorTheme
├── editor background
├── editor foreground
├── margin colors
├── caret color
├── comments
├── keywords
├── strings
├── numbers
├── operators
└── preprocessor directives
```

Initially there may be only one theme:

```text
TIGCC Dark
```

But the design should leave room for:

```text
TIGCC Dark
TIGCC Light
System
Custom
```
  
  

#### 3. Stabilization and regression tests

Before adding major new functionality, establish a small repeatable test checklist for all three backends:

```text
open file
edit
save
save all
discard
close tab
close all
quit
project transition
backend transition
multiple tabs/sessions
```

For Vim, include:

```text
manual :w
manual :wq
manual :q
read-only files
multiple independent Vim sessions
```

This is especially important because the Vim backend uses asynchronous state files and nested event loops, making regressions easier to introduce.
  
  

### Soon-ish: application configuration

After editor API parity, the next major application-level feature should be configuration.

The configuration system should eventually store:

```text
default editor backend
default editor font size
editor theme
possibly recent projects
```

A reasonable initial configuration model is:

```text
Configuration
├── editor backend
├── editor font size
├── editor theme
```

#### Recommended storage

JSON is consistent with the existing project persistence.  
  
A JSON format would be reasonable:

```json
{
"editor": {
"backend": "qscintilla",
"fontPointSize": 12,
"theme": "tigcc-dark"
}
}
```

The configuration interface should be independent of the widgets that consume it:

```text
Configuration
reads/writes settings

MainWindow
applies settings

EditorBackend
receives editor-related settings
```

#### Recommended order

1. Define configuration data.
2. Load configuration during startup.
3. Apply default editor selection.
4. Apply default font size.
5. Save changes when settings are modified.
6. Add a preferences interface later.

The configuration file itself should come before the preferences dialog. That lets us test persistence without first building a large settings UI.  
  

### Project tree and file model

#### Immediate small improvement

Widening the project-tree panel by approximately 40 pixels is a low-risk UX improvement and can be done soon.
  

#### Next project-tree work

The next major tree change should be to formalize file categories.

A scalable model might contain:

```text
Source Files
Header Files
GNU Assembly Files
m68k Assembly Files
Linker/Configuration Files
Text Files
Other Files
```

The exact categories should be based on the expected TIGCC project structure and examples from KTIGCC, but the implementation should use a generic category model:

```cpp
struct ProjectFileCategory
{
    QString name;
    QString directory;
    QStringList extensions;
};
```

Then adding a new file type becomes primarily data/configuration rather than another branch throughout:

```text
Project model
Project manager
Project tree
New-file menu
```

The default output directory belongs here as well:

```text
project/
├── src/
├── include/
├── gas/
└── output/
```
  
### Later, before compiler integration

#### Completion data scheme

This is likely the largest editor-side task before TIGCC integration.

The completion system will be separated into at least two layers:

```text
CompletionData
- Loads/parses TIGCC definitions

CompletionProvider
- Supplies matching symbols to an editor backend
```

The backend-specific adapters would then be:

```text
QScintilla completion adapter
KTextEditor completion adapter
Vim completion adapter
```

A useful generic model might include:

```text
symbol name
symbol kind
signature
return type
documentation
header/include information
target/language applicability
```

For example:

```text
Symbol:
name: printf
kind: function
signature: printf(const char *, ...)
documentation: ...
```

The completion data source should not be tied directly to QScintilla or KTextEditor. The format parser belongs in a TIGCC/editor-independent module.

The order should be:

1. Determine the existing TIGCC completion-file format.
2. Design an internal symbol model.
3. Implement a parser.
4. Add lookup/filtering.
5. Integrate with QScintilla.
6. Integrate with KTextEditor if retained.
7. Determine what can realistically be exposed to Vim.

Because Vim is a terminal-hosted external editor, completion integration there may require adifferent mechanism, such as:

```text
Vim completion configuration
Vimscript/Lua integration
generated completion files
temporary symbol files
```

That is another reason to keep the completion data scheme independent of the editor backend.  
  

### Much later: compiler integration

We will implement a  `CompilerBackend`, consistent with the rest of the architecture.

Even though TIGCC is currently the only intended compiler, the abstraction remains valuable:

```text
MainWindow
↓
CompilerBackend
↓
TIGCC compiler implementation
```

The first interface should probably cover:

```text
configure project
build project
clean project
cancel build
query compiler availability
collect diagnostics
```

A provisional API might eventually look like:

```cpp
virtual bool
isAvailable(
    QString *errorMessage = nullptr
) const = 0;

virtual bool
buildProject(
const Project &project,
    QString *errorMessage = nullptr
) = 0;

virtual bool
cleanProject(
    const Project &project,
    QString *errorMessage = nullptr
) = 0;
```

The implementation should be asynchronous rather than blocking the GUI:

```text
CompilerBackend
launches process
captures stdout/stderr
parses diagnostics
emits progress
emits finished
```

The build-output widget then becomes a consumer of compiler events rather than a passive text area.  
  

#### Initial compiler milestone  

The first compiler integration should be deliberately narrow:

```text
Build Project
↓
compile one C source file
↓
display compiler output
↓
report success/failure
```

Only afterward should we add:

```text
multiple source files
assembly
linking
output installation
calculator transfer
```
